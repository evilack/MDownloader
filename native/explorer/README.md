# Windows Explorer bridge

This optional bridge is solely for revealing files written directly through a picked folder handle. It does not extract, transfer, transcode, or download media. It uses Windows PowerShell already supplied with Windows; no Python/FFmpeg/runtime installation. Ordinary browser downloads continue to use Chrome's native `downloads.show` without this bridge.

The normal Windows setup entry is **Settings → Download location → Select folder**. If the helper is absent, the extension asks before changing the folder. Cancel keeps the current folder and opens no picker. Install downloads `MDownloader-Windows-Setup.cmd`; after completion, **Run installer** opens that file. Chrome/Windows may request execution confirmation. Installation copies/registers the helper and verifies a framed ping automatically, using the current extension ID without asking the user to enter it. The same bundled setup works in development and Store; it adds no YouTube code to Store. Mac skips this helper and its completed-folder button opens Downloads.

If execution confirmation stalls or opening fails, **Show installer** reveals the actual downloaded file through Chrome's own API. Execute that file and return to settings; native ping must succeed before the original directory picker can continue. The UI never claims installation succeeded based only on a download/open API response.

For maintainers, the equivalent CLI registration changes the current user's Chrome NativeMessagingHosts registry and copies the bridge to LocalAppData\MDownloader\ExplorerBridge. Run only within the user's authorized setup scope:

`powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\native\explorer\install.ps1 -ExtensionId <actual-unpacked-extension-id>`

On the first reveal for a previously selected folder, choose that saved folder once in the Windows dialog. The bridge checks its leaf name, saved filename, file size, and bounded first/last128KiB fingerprint against the browser-granted file before remembering the binding. Later clicks directly launch SystemRoot\explorer.exe with `/select` on that file. It accepts no client-supplied absolute path, executable, or command. The native messaging manifest restricts callers to explicit extension IDs. Bindings are scoped by extension origin and directory key; they contain local folder paths and remain on this computer.

Settings → Download location now includes **Remove Windows helper** on Windows. Its confirmation explains that helper files/folder links are removed, downloaded videos/subtitles are retained, and the location returns to the browser default. Cancel changes nothing. A legacy installed helper uses the bundled removal CMD; Chrome may require a separate file-execution confirmation.

New installations and upgrades also register **MDownloader Windows Helper** under Windows Settings → Apps → Installed apps, for the current user without elevation. That entry launches the same uninstaller with a native confirmation (No by default). The uninstaller validates its exact LocalAppData\MDownloader\ExplorerBridge root, rejects directory junctions and foreign registrations, removes an explicit allowlist of helper files plus folder bindings/lifecycle data, and removes only its own NativeMessagingHosts and Uninstall keys. It removes a directory only if empty. Other files, including media inside that directory, are retained. Completed download records and their browser file handles remain available for playback; the selected location becomes the browser default. The unrelated Kakao helper is not modified.

The native host acknowledges scheduling, then a detached desktop worker waits for the host to exit. Only after file removal and both registry deletions does it send a random installation-identity receipt to the shipped extension lifecycle page. The page matches the stored identity and verifies the native host is absent before resetting both downloadFolder and pickedDownloadFolder in one storage write. A missing host alone never counts as successful removal. Startup/settings focus can retry a received receipt interrupted during consumption. Client routing records the running Chrome executable/user-data root and targets installed profiles; a bounded, shared read of only that extension's recent storage logs covers profiles whose Preferences have not flushed yet. No Chrome databases are edited.

Maintainer command: powershell.exe -NoProfile -ExecutionPolicy Bypass -STA -File "%LOCALAPPDATA%\MDownloader\ExplorerBridge\uninstall.ps1". Omit -Confirmed for the normal confirmation. The switch exists for authorized scripted verification. Installed files run under the desktop user context so ordinary Chrome can find the same registration.

Automated tests use `-TestMode` with a temporary directory and do not show an OS picker or launch Explorer. This proves framing/validation/binding/fingerprint behavior, not an installed Chrome-to-host or observed Explorer window. Those unit tests alone do not prove installed Chrome/Explorer acceptance; the dated evidence below records the separately authorized live checks. First-time folder linking requires a user gesture and manual folder selection; it is not silently inferred from a handle.
